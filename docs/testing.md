# Testing: what checks exist and when to run them

| check | covers | run | time |
|---|---|---|---|
| `cd crates/xdj-fw && cargo test --release` | the firmware codecs against the real 2.21 image: ISO / cramfs / tar round trips, a no-change build reproducing every file, overlay build, unpack → edit → repack | after touching `crates/xdj-fw` | ~5 s |
| `tools/xdj-panel/test_panel_parity.py` | the in-process Rust panel (`app/host/src/panel.rs`) vs `server.py`: every control snapshot, HTTP reply, LED and log line for one scripted session | after touching either panel server | ~30 s |
| **`tools/test/regress.py`** | the whole thing, live, on a throwaway unit (private `$HOME`, runtime dir, ports) | before merging anything that touches QEMU, the host, the panel or firmware handling | ~8 min |
| `tools/test/stress.py` | a custom firmware (3.00 and later) under hours of random use: every feature, stick swaps, power cycles, safe starts; records each crash | before a firmware release | hours (until a deadline) |
| `tools/test/make-test-sticks.sh [--big]` | builds the test sticks (`test/usb/gen_*.img`) from synthetic audio | once, or after changing it | ~1 min, ~4 min with `--big` |

## `tools/test/regress.py`
`--app dist/XDJ-RX.app` tests the **packaged** app (its host, relocated QEMU and panel files) instead of
the build tree. Stages (`--only` picks a subset; `--unit DIR` clones an installed firmware dir instead of
provisioning; `--keep` keeps the work dir; on failure it is kept anyway, with `host.log`,
`run/console.log`, `run/qemu.log` and every screendump):
- **prep** — `xdj-host prep` of the firmware zip.
- **provision** — a blank unit installs itself (ALL update): env `release=2.21`, then the host
  boots it from NAND by itself.
- **boot** — normal NAND boot reaches the home screen.
- **panel** — MENU *held* 2 s opens UTILITY, a short MENU tap leaves it (a short tap on the home
  screen does nothing — not a bug); rbp's LED stream is live; MCP (`POST /mcp`): handshake, tool
  list, a held `press menu`, a PNG `screenshot`.
- **usb** — BROWSE, then a panel USB LOAD of `test/usb/*.img` on **USB1** (the browser shows USB1)
  → the stick's rekordbox library replaces "NO USB". It loads a copy in its work dir: slots are
  read/write, so the fixture stays pristine.
- **standby** — POWER off while rbp runs → the standby handshake (rbp answers 'S', power cut < 10 s).
- **testmode** — File > Power On in Test Mode → VERSION INFORMATION (one retry for the known ~1-in-8
  rbp-side flake; the result notes it).
- **custom** — `tools/fw/make-test-upd.sh` builds TEST.UPD one release above what's installed,
  installs it with File > Install Firmware Update (`POST /install-update`) → env release, USER
  UPDATE + signature lines, the complete screen, both console markers, test mode right after.

Screens are classified from pixel statistics (`stats()`: black/white/colour/blue/red fractions,
printed with every result) — no reference screenshots, since the UI is Pioneer's. Run it with
nothing else heavy on the machine (single-core TCG boots are load-sensitive).

## Test sticks: `tools/test/make-test-sticks.sh`
Every stick image is git-ignored (`test/usb/*.img`) and none needs personal music or downloads:
the script builds them from synthetic drum loops and tones (macOS; ffmpeg, flac, baken).

| image | contents |
|---|---|
| `gen_lib_exfat.img` | exFAT, rekordbox library (export.pdb + analysis generated by baken): playlist "Test" with MP3, FLAC 24/96, WAV 24/96 and float WAV tracks, beat grids, hot cues A–H in rekordbox colours |
| `gen_lib_fat32.img` | the same library on FAT32 |
| `gen_flac.img` | FAT32, no library: tagged FLAC tones + WAV/MP3 controls (`mods/flac/make-flac-test-image.sh`) |
| `gen_wav.img` | FAT32, no library: the wav mod's tones, 16/24/32-bit, float, 44.1–192 kHz |
| `gen_big10k.img` (`--big`) | rekordbox library of 10,000 short MP3s (hard links of one file), playlists of 100 / 1,000 / 3,000 / 10,000 |

baken computes waveforms from the audio (`--generate-analysis`); grids and hot cues come from the
XML the script writes. Hot-cue colours are snapped to rekordbox's palette.

## `tools/test/stress.py`
Runs against an **already running** private host whose unit has the firmware installed (the mods'
test loop: [firmware-mods.md](firmware-mods.md), skill `firmware-mods`), until a deadline:
```
tools/test/make-test-sticks.sh --big             # once
python3 tools/test/stress.py --until 08:00 [--port 18765] [--unit build/T/fw] [--seed N] [--out build/stress]
python3 tools/test/stress.py --safe-starts 5     # only safe-start power cycles, then exit
```
`--unit` is the unit's directory (the script reads its `run/console.log`). Needs Pillow (screens
are told apart by a pixel colour: browser, deck, UTILITY).

- **Actions**, weighted at random (`--seed` repeats a run): browse + load (library and
  [FOLDER]), play/pause, jog + tempo + crossfader, hot cues A–D, SHIFT + pad E–H, beat jump, a
  UTILITY setting, stick insert, pulling the stick under a loaded/playing deck, [FOLDER] /
  Contents, the 10,000-track scroll, power cycles (one in four a safe start, then a normal boot).
- **Checks after every action**: crash text on the console (segfault, abort, oops, relocation
  error, out of memory, …), the console restarting on its own, host status (power, `rbp_running`),
  frames still being drawn (the fps mod's 10 s log line; > 45 s without one = frozen UI). A safe
  start must log the MIDI marker and must not load the mods.
- **On a failure**: `OUT/crashes/NNN/` gets `reason.txt` (the reason and the last 60 actions),
  `console.log` and `screen.png`; the unit is power-cycled and the run goes on. `OUT/report.md`
  is the running summary (actions per kind, boots, crashes, ALSA xruns), `OUT/log.txt` the log.
- ALSA xruns are counted, not failures: the emulator produces them steadily (normal level: about
  one every 15 s of use).
- Safe start holds MIDI (`POST /mainkey 161`) from the first console output until
  `#### Application Start!! ###`, then releases it (`/mainkey_release`): the key check comes right
  after the USB hub setup, which in the emulator can stall a boot for minutes
  ([emulator-status.md](emulator-status.md)), so no fixed hold time is safe.

**3.00:** a 6-hour run (1,453 actions, 31 boots, 8 safe starts) had no firmware crash; its one
recorded failure was the harness's fixed-length MIDI hold ending during a hub stall, before the
key check.
